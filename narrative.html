Objective

The idea with this project is to methodically design a hosted AI agent based on $100M Money Models so that you can get a feel for how I work through design and build problems.

When a user says things like, "I think CAC is too high," "cash is tight," "what should I add after the first sale?" the advisor should reply with explanations, diagnosis, and/or recommendations - citing passages from Money Models where appropriate.

The advisor exists today as a local CLI core, driven by the coding agents of both candidate providers — Codex for OpenAI, Claude Code for Anthropic. That's the method: settle the design choices that need evidence — platform, model, retrieval strategy — in a cheap harness before building the hosted version (§3.8). The hosted build is the next step, not part of this write-up.

1.1Scope

Three parts of this system are probably overkill: the vector database, semantic retrieval, and namespace partitioning (ditched for a single namespace after it showed no benefit and latency costs during testing). I included these elements in the design process because the Sr. AI Engineer role calls for them.

An early prototype that used a decision tree .md file and several framework summary files (created from transcripts of the Money Models video course) in a Claude project performed pretty well in informal testing.

Design

This is the design of the hosted advisor. The agent makes every judgment call; a deterministic core does everything else.

2.1Workflow

One advisory turn starts with a founder's question and ends with an answer plus an auditable record of how the answer was produced.

Founder asks a business question → agent reads what the advisor already knows about the business → agent decides whether to clarify, calculate, diagnose, or consult the book → deterministic services perform the repeatable work → agent judges the results and writes the answer → the system validates the evidence and records the turn

The boundary is the central design rule: the agent owns meaning and judgment; the deterministic core owns state, formulas, retrieval, validation, and recording. The component map below shows where each responsibility lives; the sections after it unpack those components in the same order.

Component map

The agent — judgment
Model gpt-5.4-mini + gpt-5.5, chosen by testing every candidate from both providers; the core stays model-agnostic. §2.2
Instructions One versioned skill file, hardened like code through a test-fix loop. §2.3
Deterministic core — everything else
Tools Eight operations, bounded by one session start and finish. §2.4
Memory Typed business state, every field source-tracked, reused each turn as the context cache. §2.5
Knowledge The book, chunked and indexed in a vector store; hybrid BM25 + vector retrieval. §2.6
Guardrails No ungrounded citation, no unproven math — enforced at session finish. §2.7

A hosted service on the OpenAI Agents SDK, taking the founder's business data as uploaded context — today a local CLI reading the founder's files in place. §2.9

2.2Model

The planning brain runs on two OpenAI models: gpt-5.4-mini makes the source-need decision, gpt-5.5 sequences the tools across a turn. Both were picked by running every candidate model from Anthropic and OpenAI through the same golden cases (§3.8). The core stays model-agnostic, so a model can change without touching the tools, memory, or retrieval around it.

2.3Instructions

The agent's instructions are one versioned skill file (SKILL.md, 238 lines): how to run a turn, when to search versus ask, the query variants each search requires (§2.6), and what the trace must contain at the end. It's treated like code — versioned in git and amended through the test-fix loop in §3.9: when one agent misreads an instruction the skill is patched, and when two fail the same way the case becomes a regression test.

2.4Tools

The CLI (§2.1) emits structured JSON the agent reads. Six of its eight operations run in the order a turn uses them; logs and index pinecone are utilities used outside that flow.

session start
Prepare the turn: load the snapshot; show advisory status, known and missing facts, retrieval hints, recent turns, available operations, and what must be recorded at the end. It does not answer, decide the next action, or search.
snapshot / snapshot set
Read and persist accepted facts. Validates field paths, recomputes readiness; never infers facts or decides which matter.
calculate
Deterministic formulas — CAC, gross profit, gross margin, lifetime gross profit, payback period, CFA (client-financed acquisition) level. The agent must not do this math from memory.
diagnose
Deterministic unit-economics diagnosis from saved numbers. The agent decides whether the result is relevant and how to explain it.
search
Retrieve citation-ready chunks from an agent-written SourceNeed, against a selectable retrieval strategy and vector store (§2.6).
session finish
Validate and persist the completed turn as one structured artifact: message pair, actions, source events, calculation events, cited chunk IDs, ending snapshot.
logs
Inspect prior turns when the conversation depends on earlier context.
index pinecone
Index management: upsert corpus vectors into the hosted vector index (§2.6).

2.5Memory

The advisor's memory of a business is one typed object — identity, offer stack, economics, problem framing — and every field records where it came from.

V1 stores only what's needed to decide the next advisory action, run diagnostics, target retrieval, and explain what's missing before a recommendation. The whole schema:

Block by block:

business
Who the business is: business_type, icp (ideal customer profile), delivery_model. These change how the book's examples apply and how fulfillment cost and margin should be read.
money_model
The book's five offer types — attraction offer, core offer, upsell, downsell, continuity — each stored as {exists, description, price}. exists alone wouldn't be enough — "add an upsell" is bad advice for a business that has one but priced it too low — so the description and price are stored with it. And exists takes three values: true, false only when there's evidence the offer is really absent, and null when nobody knows yet.
economics
The unit-economics numbers: cac (customer acquisition cost), first-30-day and recurring gross profit, gross margin, lifetime gross profit, and the derived payback_period_months — recomputed whenever inputs change.
problem
The user's goal, their symptoms in their own words (reported_symptoms: "cash is tight"), and the advisor's conclusions (diagnosed_constraints: slow_payback) — separate fields, so what the user reported is never confused with what the advisor concluded.
advisor_state
Status fields the CLI computes and the agent can read but not invent: which diagnoses the saved numbers can support, the still-missing facts — which is what drives the clarifying questions — and which sections of the book are likely relevant. The agent decides whether any of this matters for the current turn. The headline field, advisory_status, moves through four stages:
insufficient_context→ diagnosable→ diagnosed→ recommendable
field_sources
One record per saved fact, naming where it came from (file, conversation, or calculated) with a confidence grade and timestamp. Facts taken from a file keep the file's path and a hash of its contents, so the fact is marked stale when the file changes. The record for a CAC read from a metrics file: 
"economics.cac": {
  "source_type": "file",
  "source": "metrics/q1-unit-economics.csv",
  "source_hash": "abc123",
  "confidence": "high",
  "updated_at": "2026-06-05T00:00:00Z"
}

Merge rules are explicit — inspected evidence beats inference, direct user statements beat weak file inferences, newer direct user statements beat older ones — and conflicts are preserved in the trace rather than silently overwritten.

The snapshot is also the cache for business context: facts are accepted once and reused every turn after — the advisor remembers the business, advice traces to sourced facts, and docs aren't re-inspected every turn. Full schema, field rationale, readiness and merge rules: BUSINESS_SNAPSHOT_V1.md.

2.6Knowledge & retrieval

Every search starts from a structured request the agent writes — a SourceNeed — and runs hybrid: two rankers over the same chunked book, BM25 and vector, combined into one ranked list.

The corpus: 32 lesson transcripts, labeled by subject

The source material is the book's lessons — 32 transcript files, one per lesson, about 88,000 words. Each lesson is labeled with the subjects it covers — often more than one:

unit-economics offers upsells downsells continuity

The request: a SourceNeed

A SourceNeed is the structured request the agent writes for one search. Its fields:

subjects
Which book subjects to search, drawn from the five above. Restricts the search to those subjects' chunks.
focus_terms
The specific terms the search is about, e.g. CAC, payback period.
query_variants
The 2–4 rephrasings that actually run against the store (built as described next).
user_turn
The user's message, kept for context.
intent
An audit label for why the search is happening — recorded in the trace, not used to build the query and not graded by the eval (§3.1). One of:
  • teaching_evidence — explain a concept.
  • diagnostic_evidence — read the business's own economics to identify the constraint.
  • comparison_evidence — compare two concepts or options.
  • recommendation_evidence — back a specific fix once the constraint is known.

What gets searched is set by subjects, focus_terms, and query_variants. One search does one job: a turn needing two kinds of evidence runs two searches and records two source events.

Query generation: an open, eval-gated choice

The trace schema can record 2–4 variants plus a mechanical fallback, and the evaluation runner can execute and rank-fuse them. That is a capability, not yet the selected product behavior. The earlier retrieval experiment supplied already-written variants, reviewer-selected focus terms, and expected subjects; it proved that the retriever can use good inputs, not that the product can generate those inputs. A recorded request shows the trace shape:

The current generation experiment starts earlier: user question plus the normal saved snapshot, with reviewer labels hidden and no subject filter. It compares the raw question, one unguided model rewrite, and one rewrite guided by the book's glossary and frameworks. A precommitted v2 guided prompt now leads the development split by using the guide as a translation reference while preserving every concept the question actually requires. Multi-query fusion remains a candidate to test fairly, not an assumed default (§3.4).

How a search runs

Chunking
Heading-aware: preserve transcript sections, fall back to fixed windows. 202 chunks with stable IDs and citation metadata.
Search
BM25 and embedding-based vector search run over the same chunks, then their two ranked lists are merged by position, not score — reciprocal-rank fusion. The two engines' scores aren't on the same scale, so adding the raw numbers is unreliable; merging by rank position (1st, 2nd, 3rd) needs no such conversion.
Embeddings
OpenAI text-embedding-3-small embeds chunks and queries. One model so far — the 3-small vs 3-large comparison is queued (§4).
Results
Each search returns the top 5 chunks (CLI default --top-k 5), each with a stable ID, its score, and citation metadata. The agent reads them and decides which actually support the claim — a top rank is never taken as proof the chunk is relevant.
Cost control
Corpus and query embeddings are cached under .cache/embeddings/; warm eval runs make zero external embedding API batches.
Storage
A narrow VectorStore interface with two implementations: local in-memory for fast dev and evals, and Pinecone for hosted retrieval. The first Pinecone adapter is a small REST client rather than the official SDK; it can move to the SDK later without touching advisor or eval logic. The index also supports a namespace-per-subject layout; a single namespace with metadata filters is the default (§3.7).

None of these choices was assumed. Section 3 is the measurement behind each: how it was tested, and why it was kept or rejected.

2.7Guardrails

Before a turn is saved, session finish checks it against fixed rules rather than trusting the agent's self-report. Two can reject the turn outright:

Grounded citations
Every cited chunk ID must appear in a source event, unless the trace explicitly marks it as an external, non-corpus citation — the agent cannot quietly cite material it never retrieved. Chunks inspected but not cited only warn: that's legitimate behavior. This is the grounding rule: a claim about the book either cites an inspected chunk or isn't made as a book claim at all — when retrieval finds no support, the advisor has to say so instead of inventing a citation.
Proven math
If actions include calculate, the trace must include structured calculation_events with metric, inputs, and output — added after agents were observed claiming math their traces couldn't prove (§3.9).

2.8Observability

Every turn is persisted as one structured artifact — message pair, actions, source events, calculations, cited chunks, ending snapshot — and every eval in §3 reads these traces.

Actions
A non-empty list of known operation labels. Zero source events is valid — not every turn should search.
Source events
Each must carry the full SourceNeed, the executed queries, and inspected chunks with IDs and scores.
State
The ending snapshot is captured automatically.

2.9Environment

The hosted advisor will run as a service on the OpenAI Agents SDK, taking the founder's business data as uploaded context. Today it runs locally instead: pointed at the founder's business directory (--business-dir), the agent reads those files in place when saved context is missing and records each accepted fact back to its source path and content hash (§2.5). A hosted service would copy the directory in first; the local CLI just reads it where it lives.

Tested today as a local CLI

Two coding agents operate the local core: Codex and Claude Code. The CLI came first because it is a cheap way to settle the provider choice before building the hosted version — running the same core through both agents compares OpenAI and Anthropic on the same workflow (§3.8). The hosted version will run this core on the OpenAI Agents SDK. Because the coding agents are flat-rate subscriptions rather than per-token API calls, embeddings are the only per-use cost today, cached after first use (§2.6).

The only outside services today are the embedding API and the Pinecone vector store (§2.6).

Method

3.1Evaluation framework

The evals run in order so a failure points at one component. Agent judgment is tested before query writing, and query writing before the retriever. So when two retrieval strategies differ, the difference is about retrieval, not a bad query or a wrong decision upstream.

  1. Tool-use judgment Should this turn search source material at all — versus read state, inspect docs, calculate, clarify, or answer directly?
  2. Source-need generation When search is right, what should guide it: what to look for, which corpus subjects to search, and which concepts to cover?
  3. Search-query quality Does query construction retrieve citeable chunks for that source need?
  4. Strategy comparison Only now do BM25-vs-vector-vs-hybrid comparisons measure which method ranks the right passage higher.
  5. Support coverage Do the cited chunks actually support the claims the answer must make?

Five of the nine datasets each test one of the steps above. The other four check the eval system itself: two verify traces record what actually happened (source events, calculation events), one compares chunking strategies, and one audits whether eval queries are phrased the way real users talk. Every dataset pairs with an automated scorer that writes an auditable report. The acting agents in the judgment evals are subscription coding agents — Codex for the reference results here, and both Codex and Claude Code in the model-selection sweep (§3.8). OpenAI's API is used only to turn text into vectors for search.

Blind, three roles
An acting agent performs each case using the skill and CLI without seeing expected labels. A trace extractor maps its observable behavior — commands run, files read, snapshot diffs — into recorded actions, marking weak evidence as inferred or missing so it stays visible. A separate scorer compares those actions to the labels. The score comes from what the agent did, not from what it says it did.
Label strength
"Do not search on this turn" is strict: searching fails the case. "This chunk is known useful" is a starting label, not a complete list of every useful chunk. Exact term matching is only a debugging signal — "front-end offer" fails a text match against "front end offer" — so the measure that counts is whether the concepts are covered, judged with a written rationale. Misses against the starting labels get reviewed before they're counted.

3.2Quality scoring

The tool-use suite has 24 cases. Most were captured during the build as development and regression traces; the rest are held-out scenarios, run after the instructions were frozen, by acting agents that never saw the expected answers. The source-need suite has 14 cases: 10 where the right move is to search, 4 controls where it isn't. Results: all 24 tool-use cases passed with full required-action recall and zero false and zero missed searches. Source-need scored 100% on the search/no-search decision and matched the expected subjects exactly on 9 of the 10 search cases. The misses, case by case:

Corrected label
One held-out case required reading logs as the literal first action. Review concluded that reading the snapshot first did no harm — the logs were still read before answering — and the label records that review explicitly.
Unresolved miss
On the free-trial case the agent picks the offers subject without also adding downsells. It remains open.
General rules, not patches
When a case disagreed with its label, the resolution became a general rule, not a one-case patch. Two examples: payment plans are labeled downsells — they look like pricing, but their function is reducing purchase friction. And a search that interprets the business's economics stays on the unit-economics subject even when the answer will recommend something; the recommended move gets its own search on its own fix subject. One answer, two searches — so each search ranks against only its own subject's passages.
Decision

Agent judgment is solid enough to build the retrieval comparisons on.

With search/no-search decisions at 100% on the captured sets, the agent reliably picks the right action, so differences between retrieval strategies reflect the retrieval itself.

3.3Chunking strategy

Two chunking strategies were compared on a labeled set. Heading-aware splits the transcripts at their section headings. The framework-aware variant adds split points at cue phrases like "how it works," "step one," and "examples" — the spots where a lesson switches from naming a framework to explaining it — on the theory that tighter chunks would match definition-style and mechanics-style queries better. It didn't help: identical Hit@1 (81.25%), and an MRR gain of +0.0041.

Decision

Keep heading-aware chunking.

A gain of less than half a percent doesn't justify maintaining a second chunking pipeline; the comparison stays in the repo as a recorded non-adoption.

3.4Query generation

Once the agent decides what to search for, that decision has to become an actual search query. The first version did the simplest thing — take the key terms and run them as one query. It worked on most turns and failed on one clear kind of question (§2.6):

The question
"Why does fulfillment cost matter for whether ads can work?" The user is asking why one thing affects another, not just for a definition.
What went wrong
The one-query builder just strung the terms together — gross profit, fulfillment cost, CAC, payback. A bare list doesn't say the user wants the link between them, so the search brought back nearby chunks about payback and CAC and ranked the one passage that actually explains the fulfillment-cost-to-gross-profit connection too far down. The right chunk existed; the query just didn't surface it. The problem was the query, not the search engine.
The earlier candidate
Run three short rephrasings plus a deterministic keyword fallback, then use reciprocal-rank fusion to promote chunks that recur. This worked well as a retrieval experiment, but the variants were a frozen fixture with no recorded generator. The evaluator also supplied reviewer-selected focus terms and expected subjects and used those subjects as filters. That means the result begins after the hardest generation choices have already been made.

The new experiment starts at the real product input instead: the user's question and normal saved business snapshot. It hides the reference query, focus terms, subjects, and useful chunks; applies no subject filter; and runs one query. All five rows below use the same enriched 30-case labels and local hybrid retriever, but the first row has more information and four searches, so it is a ceiling rather than a fair generation head-to-head.

Guided v2 was committed before generation. It tells the model to use the guide as a translation reference, preserve however many concepts the user's mechanism or relationship actually needs, and omit only concepts added because they are nearby in the guide. Against v1 it tied 23 cases, improved four ranks, repaired both top-five misses, and regressed one case from rank 1 to rank 2. It clears the declared development gate and closes much of the gap to the old four-query ceiling while using one query and no subject filter. It is now a holdout finalist—not a production decision. The 16-case holdout remains unopened until its relevance labels are human-reviewed.

§3.5 isolates the retrieval backends while holding the old fixed variants constant. Cost: about four searches per case, 120 across the 30-case set. Embeddings are cached, so on repeat runs those searches made no new embedding API calls.

3.5Hybrid retrieval + reranking

BM25 served as the keyword baseline and control, not the product architecture. Its job was to reveal whether vector and hybrid retrieval actually beat the simple thing, and it set a high bar — the generated queries carry the book's exact framework terms ("CFA," "rollover upsell," "payback period"), and that shared vocabulary makes keyword retrieval unusually competitive. Against it: vector search and rank-fused hybrid, over the same chunks, each running the frozen constrained query variants described in §3.4.

The comparison is graded at Hit@1 — did the single best labeled chunk come back first. The known-useful labels mark only some of the good chunks, not all of them, so before trusting that grade, every case where a backend did not rank a labeled chunk first was checked by reading the chunk that actually came back. Where that chunk directly answered the turn but had never been labeled, it was added to the answer key — the same correction applied to BM25, vector, and hybrid alike, so no backend got a friendlier key.

At Hit@5 the methods tie near 100%, which on a corpus this size says little. Hit@1 is where they separate: hybrid + variants ranks the right chunk first on nearly every case (mean rank 1.03), ahead of the BM25 control and vector. After the answer-key correction, hybrid carries one genuine remaining weakness against BM25's three and vector's four. The one weakness shared by all three is a case where an anecdotal passage outranks the explanatory one — a content issue, not a retriever one. On 30 cases the whole gap is only a few cases, so the mean rank and the count of real weaknesses are stronger evidence than the percentages.

Decision

Hybrid remains the candidate retrieval backend and BM25 remains the control. Holding the supplied queries fixed, hybrid ranks useful evidence best on this slice—but only by a few cases.

Guided v2 is the single-query development finalist, not yet the product default. The old fixed-variant result remains a downstream ceiling; v2 and any fair multi-query challenger must earn adoption on the reviewed holdout.

3.6Latency benchmarks

Local retrieval came first so iteration and evals stayed fast. Once the strategy was justified, the same 30-case set was rerun against the Pinecone implementation of the VectorStore interface (§2.6): 100% Hit@3/Hit@5, mean useful rank 1.17, 100% query-cache hit rate, and no new embedding API calls — the cache served every query. Quality reproduced exactly.

What the latency benchmark exposed instead: the first hosted run executed each case's four query variants one at a time, and p50 retrieval landed around 5.3s for hybrid and 5.5s for vector — versus sub-millisecond local BM25. Running the variants in parallel (8 workers) brought the same 30-case benchmark to roughly 1.4s p50 and 1.8s p95, quality unchanged.

Decision

Hosted retrieval works: Pinecone returns the same results as the local store, and parallelizing the variant queries fixed the worst of the latency.

Top-k tuning and request-level observability are still open — no claim of production latency readiness before they're done.

3.7Pinecone namespaces

The corpus was indexed one namespace per subject, with the agent choosing which to query, and the same 30 cases — same variants, cache, and hybrid path — ran both ways: one namespace with metadata filters versus the five-way split. The split was routed straight from each case's expected subjects, giving it the most favorable routing it could possibly get.

The two conditions retrieved identically. Not just the same scores: across all 90 case-and-retriever rows, the same top-5 chunks in the same order. Namespaces would only help if wrong-subject chunks were crowding out right-subject ones, and on this corpus they are not. Tail latency got worse: p50 barely moved (~1.45s vs ~1.43s), but p95 went from ~1.76s to ~3.01s, on 140 vector searches instead of 120.

The mechanism: at 202 chunks, a Pinecone query is dominated by the network round-trip and fixed per-request overhead, not vector scan time — so searching a smaller namespace saves microseconds. The split instead turns one round-trip into up to five for multi-subject cases, and a case finishes only when its slowest namespace answers. Waiting on the slowest of five queries is usually slower than waiting on one — which is exactly what the p95 shows.

One scope caveat: this set is saturated — Hit@5 is 100% for every backend in both conditions — so it cannot detect a quality improvement from anything. The supported claim is "no measurable difference on this set," not "namespaces never help." If the corpus grows to where subjects interfere in ranking, re-test on a harder set.

Decision

Namespace support stays in; a single namespace with metadata filters stays the default.

The five-way split is implemented and verified, loses on tail latency, and wins nothing on quality here. It gets promoted only on a measured win.

3.8Model selection

The hosted advisor needs a model for its planning brain — the part that decides when to search, when to calculate, and when to answer from saved state. Two choices ride on it at once: which provider to build on (Anthropic or OpenAI), and how strong a model the job needs. Each provider sells a range of models — a top, expensive one down to smaller, cheaper ones — so the second question is whether the strongest model is required or a cheaper one can do it. Both are read off one grid — five models, the same 38 golden cases, the same scorers.

To keep it honest, each model operates the real CLI-backed advisor: same prep code, same 14 source-need and 24 tool-use golden cases, same deterministic scorers. It inspects state, runs the local CLI, and writes the same trace artifacts a live turn would. OpenAI models act via codex exec; Anthropic models act as a Claude Code subagent, one per case. Every model ran the full suite three times (K=3); the first gpt-5.5 attempt hit ChatGPT-subscription usage limits mid-run, and the two repeat runs completed clean once those limits cleared. Quality is comparable across providers (identical cases and scorers); token and latency figures are harness-reported proxies from two different tools, so read cross-provider cost as a ballpark, not billed dollars.

Reading the grid

The right model depends on the job. On the light source-need decision, the cheaper models win: Sonnet (92.9%) and gpt-5.4-mini (90.5%) each beat their own provider's strongest model, and either provider can do this job well. On tool-use orchestration the strongest model earns its cost, and here the two providers' strongest models separate by a real margin: gpt-5.5 leads at 91.7%, ahead of Opus at 84.7% — both measured across three clean runs. Haiku trails on both, and its tool-use score (54.2%) rules it out — about half its runs miss a required step or fire a forbidden search.

Cost

Calculation, persistence, retrieval, and trace validation all run in the CLI, so none of that work is a paid model call, on either platform. What's left is the source-need decision and tool-use orchestration; the cheaper model handles source-need almost as well as its own frontier sibling, so it routes to gpt-5.4-mini.

Where the misses cluster

Across models the strict-pass losses land on the same known-weak cases, not new ones. On source-need it is the free-trial case (offers-vs-downsells subject ambiguity, already flagged noisy in GOLDEN_DATASET.md) and a recall question that saved state already answers (over-search). On tool-use, Opus's losses are a skipped calculation and over-search, gpt-5.4-mini's are missed source-searches and diagnoses, and gpt-5.5's are the same shape — over-search and missed diagnose — repeated across its three runs. These are documented soft spots, not surprises.

Decision

Host the agent on OpenAI, and split the planning role across two models: route the source-need decision (search or not, which subject — one classification call) to gpt-5.4-mini, and keep tool-use orchestration (sequencing read / calculate / diagnose / search across a turn) on gpt-5.5. Haiku and Opus are not promoted to the planning role.

Both providers can split the planning role between a cheap and a strong model and measure the split repeatably (K=3), so that's no longer what decides it. What decides it is which side wins its harder job by more: Sonnet beats gpt-5.4-mini on source-need by 2.4 points, but gpt-5.5 beats Opus on tool-use — the job with more steps and more ways to fail — by 7.0 points. OpenAI wins the harder job by a wider margin than Anthropic wins the easier one. Embeddings already run on OpenAI's API regardless of which provider hosts the planning brain (§2.6), so hosting there too leaves one model provider in the stack instead of two.

3.9Regression detection

Beyond the planned experiments, the design was hardened by a test-fix loop against acting agents that don't know they're being tested and are graded on their saved traces, not their answers. Send realistic turns, inspect the traces, and fix the part that actually failed: skill guidance, CLI command design, trace schema, or eval case. The rule for acting on a failure is explicit: if one agent is confused by the instructions, patch the skill; if two agents fail the same way, add a regression case; anything that could corrupt state or hide unsupported advice gets a CLI guard after a single occurrence.

Trace shape → schema guard
Agents listed calculate in actions while traces didn't preserve the math. Fix: structured calculation_events, required whenever calculate is claimed (§2.7). The 5-case regression suite passes 5/5 — and one agent that nested the events under metadata was correctly rejected by the validator, confirming the guard catches the real failure class.
Source events → regression suite
On a "what should we fix first?" turn, the correct answer needs two recorded searches: diagnostic evidence plus recommendation evidence for the chosen fix. Blind runs failed twice, two different ways. After tightening the guidance, the case became a 6-case set covering multi-search, pure-diagnosis, pure-recommendation, no-search, teaching-only, and continuity turns — with counter-cases in both directions so the rule against extra searches can't be passed by simply never searching. Current: 6/6, zero extra-search warnings.
Path plumbing → CLI guard
One acting agent's shell-variable mistake pointed session start at the advisor repo itself. Fix: the skill shows a safe shell pattern, and the CLI refuses to treat the advisor repo as a business directory unless explicitly overridden.
Command design → command change
A realistic offer-sequencing turn exposed that diagnose expected raw JSON instead of reading saved state, and that agents skipped writing query variants. Fix: diagnose --business-dir reads the snapshot directly, and in that iteration query variants became mandatory — the skill requires 2–4 agent-written variants per search, session finish rejects source events without them, and a second 6/6 source-event pass verified the stricter trace contract. The new generation experiment makes that product behavior provisional: if a single-query method wins the holdout, the skill and validator must be reconciled with the measured choice rather than preserving variants by inertia.

Limits & next

Scale
Golden sets are portfolio-scale (5–65 cases each). They drive architecture decisions and catch the failure modes found so far; they are not production benchmarks. The high pass rates read as "the design clears everything that has broken it" — not "nothing will break it."
Query-variant provenance
The retrieval comparison (§3.4–3.5) holds the query variants fixed — the right control for isolating the retrieval method — but the variants themselves are a frozen fixture with no recorded generator. That old evaluator also supplies reviewer-selected focus terms and expected subjects and uses the subjects as retrieval filters. The new experiment removes those hidden inputs and records every prompt and raw model response, but its 30 cases are exposed development data. The supported claims are therefore: fixed variants demonstrate a high downstream ceiling; guided v2 is the strongest single-query development finalist; neither query count nor generator is selected until the reviewed holdout is run.
Retrieval answer key
The Hit@1 grades (§3.5) rest on a 30-case, near-saturated set — Hit@5 is 100% for every method — with a hand-adjudicated answer key: some correct chunks were added by reviewer judgment after reading what each search returned. The same rule was applied to every method, so it favors none, but the exact percentages carry that subjectivity. Mean useful rank and residual-weakness counts are cited as steadier signals than the raw percentage.
Hosted latency
~1.4s p50 / ~1.8s p95 for Pinecone hybrid after parallelizing the variant queries (down from ~5.3s sequential). Hosted quality matches local exactly; top-k tuning and request-level observability remain (§3.6).
Answer quality
The thinnest coverage in the eval suite. Decisions, traces, and retrieval are well-tested; grounded final-recommendation quality is the next dataset to grow.
Cost reporting
Embedding cost, cache hit rates, and per-run query counts are instrumented. Agent-side API billing is intentionally absent because the advisor runs through subscription agent harnesses, but the model-routing reports record each harness's token-usage proxy and latency by suite (§3.8).
Model routing
Settled in the same harness the product uses: gpt-5.4-mini for the source-need decision, gpt-5.5 for tool-use orchestration, hosted on OpenAI — its frontier model wins the harder tool-use job by more than Anthropic's wins the easier source-need one (§3.8). Still missing: embedding-model selection.

The product path forward would reuse what's built: a thin web surface over the same advisor core. That is why retrieval sits behind a vector-store interface, the CLI emits stable JSON, and the advisor logic can't tell whether its vectors are local or hosted.
