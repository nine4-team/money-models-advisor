Objective

This project designs and tests an AI advisor based on $100M Money Models. It is a portfolio demonstration of how I make and validate AI engineering decisions.

Given questions such as “Why is cash tight?” or “What should I add after the first sale?”, the advisor explains, diagnoses, and recommends, citing the source material when it relies on the book.

The current implementation is a local CLI operated by Codex and Claude Code. This makes model, workflow, and retrieval choices cheap to test before building the hosted product.

1.1Scope

This is a bounded portfolio system, not a production deployment. Vector retrieval, hybrid search, and namespace partitioning were tested rather than assumed; features that did not earn their cost were rejected.

Design

This is the design of the hosted advisor. The agent makes every judgment call; a deterministic core does everything else.

2.1Workflow

One advisory turn starts with a founder's question and ends with an answer plus an auditable record of how the answer was produced.

The agent owns judgment; the deterministic core owns state, formulas, retrieval, validation, and recording.

2.3Model

The operating agent supplies semantic judgment; the CLI makes no model calls. The model-agnostic core lets the model change without changing tools, memory, or retrieval. Tests select gpt-5.5 for orchestration and show that gpt-5.4-mini can handle bounded query writing. The local product still uses one operating agent (§3.3, §3.4).

2.4Instructions

The agent's instructions are one versioned skill file (SKILL.md): how to run a turn, when to search versus ask, how to write one corpus-guided query (§2.7), and what the final trace must contain. Failures drive instruction changes and regression cases (§3.5).

2.5Tools

The CLI emits structured JSON through eight operations; logs and index pinecone sit outside the normal turn flow.

session start
Prepare the turn: load the snapshot; show advisory status, known and missing facts, retrieval hints, recent turns, available operations, and what must be recorded at the end. It does not answer, decide the next action, or search.
snapshot / snapshot set
Read and persist accepted facts. Validates field paths, recomputes readiness; never infers facts or decides which matter.
calculate
Deterministic formulas — CAC, gross profit, gross margin, lifetime gross profit, payback period, CFA (client-financed acquisition) level. The agent must not do this math from memory.
diagnose
Deterministic unit-economics diagnosis from saved numbers. The agent decides whether the result is relevant and how to explain it.
search
Retrieve citation-ready chunks from an agent-written SearchRequest, against a selectable retrieval strategy and vector store (§2.7).
session finish
Validate and persist the completed turn as one structured artifact: message pair, actions, source events, calculation events, cited chunk IDs, ending snapshot.
logs
Inspect prior turns when the conversation depends on earlier context.
index pinecone
Index management: upsert corpus vectors into the hosted vector index (§2.7).

2.6Memory

The advisor's memory of a business is one typed object — identity, offer stack, economics, problem framing — and every field records where it came from.

V1 stores only what is needed to choose the next action, run diagnostics, retrieve evidence, and identify missing context.

business
Who the business is: business_type, icp (ideal customer profile), delivery_model. These change how the book's examples apply and how fulfillment cost and margin should be read.
money_model
The book's five offer types — attraction offer, core offer, upsell, downsell, continuity — each stored as {exists, description, price}. exists takes three values: true, false only when there's evidence the offer is really absent, and null when nobody knows yet.
economics
The unit-economics numbers: cac (customer acquisition cost), first-30-day and recurring gross profit, gross margin, lifetime gross profit, and the derived payback_period_months — recomputed whenever inputs change.
problem
The user's goal, their symptoms in their own words (reported_symptoms: "cash is tight"), and the advisor's conclusions (diagnosed_constraints: slow_payback) — separate fields, so what the user reported is never confused with what the advisor concluded.
advisor_state
CLI-computed status, readiness, and missing facts. The agent decides what matters for the current turn. The headline field, advisory_status, moves through four stages:
insufficient_context→ diagnosable→ diagnosed→ recommendable
field_sources
One record per saved fact, naming where it came from (file, conversation, or calculated) with a confidence grade and timestamp. File-backed facts keep the path and content hash so they can be marked stale when the file changes: 
"economics.cac": {
  "source_type": "file",
  "source": "metrics/q1-unit-economics.csv",
  "source_hash": "abc123",
  "confidence": "high",
  "updated_at": "2026-06-05T00:00:00Z"
}

Merge rules are explicit — inspected evidence beats inference, direct user statements beat weak file inferences, newer direct user statements beat older ones — and conflicts are preserved in the trace rather than silently overwritten.

Accepted facts are reused across turns instead of rediscovered. Full contract: BUSINESS_SNAPSHOT_V1.md.

2.7Knowledge & retrieval

Every search starts from a structured request the agent writes — a SearchRequest — and runs hybrid: two rankers over the same chunked book, BM25 and vector, combined into one ranked list.

The corpus: 32 lesson transcripts, labeled by subject

The source material is the book's lessons — 32 transcript files, one per lesson, about 88,000 words. Each lesson is labeled with the subjects it covers — often more than one:

unit-economics offers upsells downsells continuity

The request: one corpus-guided query

A SearchRequest is the small traceable request the agent writes for one search. Its active fields are:

query
The single query that actually runs against the store, written from the user's question, saved snapshot, and corpus guide.
user_turn
The user's message, kept for context.
intent
An audit label for why the search is happening — recorded in the trace, not used to build the query and not graded by the eval (§3.1). One of:
  • teaching_evidence — explain a concept.
  • diagnostic_evidence — read the business's own economics to identify the constraint.
  • comparison_evidence — compare two concepts or options.
  • recommendation_evidence — back a specific fix once the constraint is known.

The query alone drives retrieval. It applies no subject or namespace filter. One search does one job: a turn needing two genuinely different kinds of evidence runs two searches and records two source events.

Query generation: measured and selected

A 46-case comparison selected a corpus-guided rewrite over the raw question and an unguided rewrite. The agent writes one query from the question, snapshot, and versioned corpus guide; the CLI runs it unfiltered through hybrid retrieval (§3.3).

How a search runs

Chunking
Framework-aware: preserve transcript headings, split long sections at framework cues, then use bounded windows as a fallback. 204 chunks with stable IDs and citation metadata.
Search
BM25 and embedding-based vector search run over the same chunks, then their two ranked lists are merged by position, not score — reciprocal-rank fusion. The two engines' scores aren't on the same scale, so adding the raw numbers is unreliable; merging by rank position (1st, 2nd, 3rd) needs no such conversion.
Embeddings
OpenAI text-embedding-3-small embeds chunks and queries. One model so far — the 3-small vs 3-large comparison is queued (§4).
Results
Each search returns the top 5 chunks (CLI default --top-k 5), each with a stable ID, its score, and citation metadata. The agent reads them and decides which actually support the claim — a top rank is never taken as proof the chunk is relevant.
Cost control
Corpus and query embeddings are cached under .cache/embeddings/; warm eval runs make zero external embedding API batches.
Storage
A narrow VectorStore interface with two implementations: local in-memory for fast dev and evals, and Pinecone for hosted retrieval. The first Pinecone adapter is a small REST client that can move to the official SDK without changing advisor or eval logic. The index supports a namespace-per-subject layout; one unfiltered namespace is the active path (§3.3).

2.8Guardrails

Before a turn is saved, session finish checks it against fixed rules rather than trusting the agent's self-report. Two can reject the turn outright:

Grounded citations
Every corpus citation must refer to a chunk recorded in a source event. Unsupported book claims reject the turn; retrieved but unused chunks only warn.
Proven math
If actions include calculate, the trace must include structured calculation_events with metric, inputs, and output — added after agents were observed claiming math their traces couldn't prove (§3.5).

2.9Observability

Every turn is persisted as one structured artifact — message pair, actions, source events, calculations, cited chunks, ending snapshot — and every eval in §3 reads these traces.

Actions
A non-empty list of known operation labels. Zero source events is valid — not every turn should search.
Source events
Each must carry the full SearchRequest, its one executed query, and inspected chunks with IDs and scores.
State
The ending snapshot is captured automatically.

Today the agent runs locally against a founder's business directory (--business-dir). A hosted version would run the same core as a service and receive those files as uploaded context.

Method

3.1Evaluation framework

The evaluation grew in stages. It covers both retrieval quality— chunking, query writing, and ranking—and the hosted implementation: Pinecone latency and namespace layout. Early tests narrowed the design space cheaply; current tests use realistic turns and passage-level judgments.

  1. Establish agent behavior A 24-turn suite tests whether the agent chooses the right action before retrieval is evaluated. The orchestration-model experiment later reuses these same cases.
  2. Screen chunking cheaply Before selecting a retrieval architecture, 32 source-oriented questions compare five chunking strategies with local BM25 held fixed. This produces an initial chunking candidate, not a final end-to-end result.
  3. Build a stronger retrieval test A separate 46-turn suite—30 base cases plus 16 expansion cases—adds saved business context and audited passage-level relevance. The query approach, query model, and retriever experiments all reuse these same 46 cases.
  4. Revalidate chunking Freeze the winning queries and replay all five chunking strategies through the selected unfiltered hybrid retriever. Measure ranking, useful-result density, and returned text—not just whether the right chapter appears.
  5. Verify the hosted implementation Index the selected chunks in Pinecone, then use the same 46 queries to measure request latency and compare one namespace with five subject namespaces: Unit Economics, Offers, Upsells, Downsells, and Continuity.

Separate trace regressions check deterministic calculations and search records. The five-case calculation suite is current; the six-case source-event suite still needs migration from the retired SourceNeed/query-variant contract to SearchRequest.query.

3.2Scoring

All 24 tool-use reference cases passed with full required-action recall, zero false searches, and zero missed searches. This clears the upstream decision—whether to search—before retrieval is tested.

Action scoring
Each case specifies required actions, forbidden actions, and any ordering constraint. The scorer reads the trace produced by the acting agent rather than trusting a self-reported summary.
Pilot chapter scoring
On the 32-case pilot, a hit means any returned chunk belongs to an expected chapter. This is the scoring used by the chunking comparison.
Current passage scoring
On the 46-case suite, Hit@1, Hit@3, and Hit@5 ask whether an audited useful passage appears by that rank. Useful@5 is the share of the five results that directly help answer the turn; Noise@5 is the remainder.
Decision

Use the 46-case passage-labeled suite for current query and retriever decisions. Keep the 32-case chapter-labeled set as a pilot baseline, not as equivalent evidence.

3.3Retrieval

Chunking strategy

Five strategies ran against the same 32-case BM25 retrieval set: three fixed windows, heading-aware transcript sections, and a framework-aware variant that adds split points at framework cues.

Answer key
Each natural-language query has a known subject and one or more acceptable source chapters.
Controlled comparison
Each strategy rebuilds the same transcript corpus. The query, local BM25 retriever, known-subject filter, and top-five cutoff stay fixed; only the chunk boundaries change.
Scoring
A hit occurs when a returned chunk belongs to an acceptable chapter. Hit@1 and Hit@5 measure whether that happens by those cutoffs. Reciprocal rank scores the first hit as 1 / rank; MRR averages that score across all 32 cases. p95 records local query latency.
Selection rule
Require 100% Hit@5 on the current suite, then compare first-hit rank, useful-result density, and context size together. A small rank gain does not win if it requires substantially more text.

This is a chapter-retrieval screen, not a passage-level test of the current runtime. A chunk counts as relevant if it comes from the expected chapter, even if that specific passage would not support the answer; the known-subject filter also makes the task easier than today's unfiltered hybrid search.

Revalidation on the current retrieval path

The five strategies then ran on all 46 current cases with the saved winning queries and unfiltered hybrid retrieval held fixed. Labels were transferred by source-span overlap, and passages exposed by new boundaries were checked for missed useful results. “Top-five words” is the total text across five results, not the size of one chunk.

Decision

Use framework-aware chunking.

It preserves 100% Hit@5 and ties heading-aware at Hit@1 while improving useful-result density and capping every chunk below 1,000 words. Fixed-800 puts useful evidence first in one more case, but returns 51% more text per top-five context.

Query generation and retrieval backend

One experiment selected both parts of the active retrieval path: how to write the query and how to retrieve with it. The 46-case matrix crosses query approach, query-writing model, and retriever.

Query approaches

Raw question
Search the user's words unchanged. This is the simplest control and adds no model latency.
Unguided rewrite
Give a model the question and normal saved business snapshot, then ask for one concise source-search query.
Corpus-guided rewrite
Give the same model the same inputs plus a compact guide to the book's vocabulary and frameworks. The guide translates the user's language while preserving every concept required by the question; it is not a checklist of related terms.

Results

Every condition uses one unfiltered query; each saved query runs unchanged through BM25 and hybrid. Generators cannot see the answer key.

False-negative and false-positive check

Across all recorded retrieval audits, we added 150 missing useful case-passage labels and removed 13 overly broad labels, for 163 corrections in total.

What the results show

Query writing. Corpus guidance performs best with both tested models and both retrievers. gpt-5.4-mini is viable for this bounded task.

Retrieval. BM25 is the lexical control. Hybrid runs BM25 and vector search, combines their ranks with reciprocal-rank fusion, ranks useful evidence earlier for both guided query writers, and preserves 100% Hit@5. Useful evidence density is mixed.

Decision

Use one corpus-guided, unfiltered query through hybrid retrieval. Keep BM25 as the control and Useful@5 and Noise@5 as regression metrics.

Latency benchmarks

The selected framework-aware chunks were indexed in Pinecone and tested with the same 46 saved queries. With one sequential product request per case and cached embeddings, single-namespace retrieval measured 4.07s p50 and 7.64s p95. It reproduced the local quality result: 93.5% Hit@1 and 100% Hit@5.

Decision

Keep Pinecone behind the storage boundary, but do not call the hosted latency production-ready. Profile the request path and tune candidate depth before adding retrieval fanout.

Pinecone namespaces

The same 46 cases compared one namespace with five subject namespaces: Unit Economics, Offers, Upsells, Downsells, and Continuity. Each test query was routed to its matching namespace. Even with this favorable setup, splitting the corpus did not improve retrieval quality.

Both layouts reached 93.5% Hit@1, 100% Hit@5, and 78.3% Useful@5. The split changed exact top-five ordering in nine cases, lowered p50 to 2.28s, and worsened p95 to 10.47s. That does not justify adding a semantic subject router.

Decision

Use one unfiltered namespace. Revisit partitioning only if a larger corpus produces measured subject interference.

3.4Orchestration model

Five OpenAI and Anthropic models ran the same 24 tool-use cases to test provider and model-tier choices for orchestration.

Each model operated the real CLI-backed advisor and produced the same trace format for the same scorer. Every model ran the suite three times (K=3). Cross-provider token and latency values are harness proxies, not comparable billed costs.

Reading the grid

gpt-5.5 leads orchestration at 91.7%, ahead of Opus at 84.7%. Haiku's 54.2% rules it out for this workflow.

In the bounded query task (§3.3), gpt-5.4-mini reaches 100% Hit@5 and 72.6% Useful@5. Its 75.0% orchestration score is not strong enough to run the full turn.

Cost

Calculation, persistence, retrieval, and validation remain deterministic. The harness supports a possible split— gpt-5.5 for orchestration and Mini for query writing—but does not establish billed-dollar savings.

Where the misses cluster

Misses cluster around over-searching, skipped calculations, and missed diagnoses or source searches. These remain regression targets.

Decision

Use gpt-5.5 for orchestration. Keep gpt-5.4-mini as the tested option for bounded query generation; the local product does not yet split the calls.

3.5Regression detection

Realistic agent runs feed a test-fix loop. Instruction failures change the skill; repeated failures become regression cases; risks to state or grounding become CLI guards.

Trace shape → schema guard
Agents listed calculate in actions while traces didn't preserve the math. Fix: structured calculation_events, required whenever calculate is claimed (§2.8). The five-case suite passes 5/5, and the validator rejects misplaced events.
Source events → migration required
Two blind failures on source-search sequencing produced a six-case suite that passed under the older SourceNeed and query-variant trace contract. The runtime now records one SearchRequest.query; the labels and scorer still expect the retired fields, so this is not a current 6/6 claim.
Path plumbing → CLI guard
One acting agent's shell-variable mistake pointed session start at the advisor repo itself. Fix: the skill shows a safe shell pattern, and the CLI refuses to treat the advisor repo as a business directory unless explicitly overridden.
Command design → command change
An offer-sequencing run exposed that diagnose required raw JSON. It now reads the saved snapshot directly. Later query experiments replaced the earlier variant contract with one recorded, unfiltered corpus-guided query through hybrid.

Limits & next

Scale
Golden sets are portfolio-scale (5–65 cases each). They drive decisions and regression checks, not production claims.
Retrieval evaluation
The 46 known cases form one audited regression suite, not an untouched production holdout. Retrieved passages were reviewed for missing and overly broad labels.
Hosted latency
The heavier Pinecone benchmark reached about 1.4s p50 and 1.8s p95 after parallelizing independent searches. The active single-query path still needs request-level measurement and top-k tuning (§3.3).
Answer quality
Grounded final-recommendation quality has less coverage than tool use and retrieval and needs a larger dataset.
Cost reporting
Embedding cost and cache use are measured. Agent-side billed cost is not available from the subscription harnesses; their token and latency figures are proxies (§3.4).
Model routing
gpt-5.5 leads orchestration and gpt-5.4-mini clears the bounded query-writing test. The local product does not yet split these calls. Embedding-model selection also remains open.
